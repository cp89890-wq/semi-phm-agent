# 실패·수정 기록

"뭐가 틀렸고 어떻게 고쳤나". 결과가 좋아 보일수록 더 의심해서 여기에 쓴다.
에이전트 오답은 반드시 분류해서 모은다 — 자소서 AI 문항의 "한계와 검증" 재료.

양식:
```
## YYYY-MM-DD — 증상 한 줄
- 어디서: (데이터 / 모델 / 에이전트 / 평가)
- 증상: 뭐가 이상했나 (숫자 포함)
- 원인: 파고 들어가서 찾은 실제 원인
- 수정: 뭘 바꿨나 → 전후 수치
- 교훈: 다음에 같은 실수 안 하려면
```

---

## 분석 파이프라인

## 2026-11-05 — 랜덤 분할이 RMSE 를 거의 절반으로 부풀린다
- 어디서: 평가(분할 설계)
- 증상: 같은 특징·같은 LightGBM 인데 랜덤 80/20 분할 RMSE 3.49, 시간순 80/20 분할 RMSE 6.11. 1.75배 차이.
- 원인: 제거율이 시간에 따라 드리프트(EDA: TIMESTAMP 상관 +0.5). 랜덤 분할은 검증 웨이퍼 앞뒤 시점 웨이퍼가 학습에 들어가 "그 시기의 제거율"을 외우게 함. 사용량(USAGE_*) 변수가 단조 증가라 사실상 시간 대리변수로 작동.
- 수정: 기본 분할을 시간순으로 고정. 랜덤 분할 수치는 비교용으로만 표기하고 벤치마크에 쓰지 않음.
- 교훈: 벤치마크 논문 수치를 볼 때 분할 방식부터 확인할 것. 분할이 다르면 숫자 비교는 무의미.

## 2026-11-05 — "챔버 2 / 챔버 5" 는 틀린 표현이었다
- 어디서: 데이터 이해(EDA 메모)
- 증상: EDA 메모에 "챔버 2(제거율~151) / 챔버 5(~77)" 라고 썼는데, 베이스라인에서 챔버를 첫 행 값으로 잡자 1/4 로 나옴.
- 원인: MACHINE_DATA 는 웨이퍼 안에서 1→2→3 또는 4→5→6 으로 바뀐다. 한 웨이퍼가 세 챔버를 순서대로 거치는 구조. EDA 에서 웨이퍼 평균을 반올림해서 2/5 가 나왔던 것.
- 수정: "챔버 그룹 123 / 456" 으로 정정. 특징 추출에서 첫 챔버 ≤3 이면 123, 아니면 456.
- 교훈: 범주 변수를 평균 내지 말 것. 웨이퍼 안에서 값이 바뀌는지 먼저 볼 것.

## 에이전트 오답 유형

2단계에서 채운다. 예상되는 유형을 미리 적어두고, 실제로 나오면 사례와 빈도를 붙인다.

| 유형 | 설명 | 사례 수 | 수정 |
|---|---|---|---|
| 상관 혼동 | 상관된 센서 둘 중 원인 아닌 쪽을 지목 | | |
| 레시피 전환 오인 | 레시피/스텝 바뀐 걸 이상으로 판단 | | |
| 근거 없는 확신 | 도구 결과가 애매한데 단정적으로 서술 | | |
| 도구 누락 | 필요한 분석을 안 돌리고 답함 | | |
| 숫자 날조 | 도구 결과에 없는 수치를 만들어 씀 | | |
